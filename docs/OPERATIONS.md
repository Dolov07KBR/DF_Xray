# Drain, миграция клиентов и сортировка по задержке

Документ про эксплуатацию нескольких нод: как вывести сервер из работы, не
разорвав клиентов, как перевести их на другую ноду и как подписка выбирает
ближайший сервер.

## Drain: вывод сервера из подписок

Кнопка с иконкой питания в карточке ноды (**Узлы → карточка → ⎋**) или API:

```bash
curl -s -X POST -H "Authorization: Bearer $TOKEN" \
     -H 'Content-Type: application/json' -d '{"drain": true}' \
     https://panel.example.com/api/nodes/3/drain
```

Что происходит:

- нода остаётся в панели, агент продолжает присылать метрики, Xray на сервере
  работает — уже подключённые клиенты не рвутся;
- нода перестаёт попадать в **новые** подписки: `xray.build_links()` её пропускает;
- в карточке появляется бейдж «выведена из подписок», в API — поле `drain: true`
  и `drained_at`;
- вернуть в работу: `{"drain": false}` или та же кнопка.

Типовой порядок вывода сервера из эксплуатации:

1. `POST /api/nodes/<id>/drain {"drain": true}` — новые подписки уже без него.
2. Перевести оставшихся клиентов на другую ноду (см. ниже).
3. Дождаться, пока трафик по ноде упадёт до нуля (дашборд → «Трафик по серверам»).
4. Остановить агент и Xray на сервере, затем удалить ноду из панели.

## Миграция клиентов между нодами

Кнопка-маршрут в карточке ноды (**Перевести клиентов**) или API:

```bash
curl -s -X POST -H "Authorization: Bearer $TOKEN" \
     -H 'Content-Type: application/json' -d '{"to_node_id": 2}' \
     https://panel.example.com/api/nodes/1/migrate
# → {"moved": 5, "from": "DF · Frankfurt", "to": "DF · Amsterdam CDN"}
```

- Меняются только клиенты с явным ограничением по серверам (`users.node_ids`).
  Клиенты без ограничений и так видят все ноды — их трогать не нужно.
- Ссылки подписок не меняются: клиент обновляет подписку и получает новую ноду
  вместо старой. Приложения с `sub_update_interval` (по умолчанию 12 часов)
  сделают это сами.
- Счётчики трафика и лимиты сохраняются, история трафика остаётся за клиентом.
- Действие пишется в аудит как `node.migrate`.

Если клиент должен остаться на нескольких нодах, укажите их в карточке клиента
вручную: миграция заменяет старую ноду на новую во всех наборах.

## Сортировка подписки по задержке

Настройка **Настройки → Подписки → «Сортировать ноды по задержке»** (по умолчанию
включена, ключ `sub_sort_by_latency`).

Как это работает:

- при выдаче подписки панель измеряет TCP-задержку до каждой разрешённой ноды
  (`xray.probe`, таймаут 1.5 с, до 8 нод параллельно);
- результат кэшируется на 5 минут (`app/latency.py`), поэтому повторные запросы
  подписки и страницы `/sub/<token>/page` не бьют по сети каждый раз;
- ссылки сортируются: ближайшие ноды первыми, недоступные — в конце;
- в каждой ссылке появляется поле `latency_ms` — его видно в `GET /api/users/<id>`
  и в JSON подписки, удобно для собственных клиентов и отладки.

Выключите настройку, если хотите жёсткий порядок: тогда ноды идут так, как заданы
в панели (поле `sort`).

Важно: задержка измеряется **от панели**, а не от клиента. Если панель стоит в
Германии, «ближайшая» нода — ближайшая к Германии. Для точной картины держите
панель в том же регионе, где основная аудитория, или выключите сортировку.

## Проверка после изменений

```bash
# подписка без выведенной ноды
curl -s https://panel.example.com/sub/<token> | base64 -d | grep -c vless

# состояние нод: drain, health, метрики
curl -s -H "Authorization: Bearer $TOKEN" https://panel.example.com/api/nodes \
  | python3 -c 'import json,sys; [print(n["name"], n["health"], "drain" if n["drain"] else "") for n in json.load(sys.stdin)["items"]]'
```
