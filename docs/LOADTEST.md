# Нагрузочное тестирование

В 1.3.0 в репозитории появился `tools/loadtest.py` — нагрузочный тест на
стандартной библиотеке, без зависимостей и внешних сервисов. Этот документ
описывает профили нагрузки, результаты прогонов в песочнице и порядок проверки
на реальных VPS с 2–3 нодами.

## Профили

| Профиль | Что нагружает | Запросы |
| --- | --- | --- |
| `panel` | работу администратора в браузере | `GET /api/dashboard`, `/api/users`, `/api/nodes`, `/api/subscriptions`, `/api/settings`, `/api/audit` |
| `agent` | агентов нод | `GET /api/agent/config` + `POST /api/agent/heartbeat` по каждому токену ноды |
| `sub` | клиентов, обновляющих подписку | `GET /sub/<token>` и `GET /sub/<token>?format=base64` |

```bash
# панель, 16 воркеров, 10 секунд
python3 tools/loadtest.py --profile panel --password 'panel-demo-2026' \
    --workers 16 --duration 10

# агенты трёх нод
python3 tools/loadtest.py --profile agent \
    --node-tokens "$(python3 - <<'PY'
import sqlite3; print(','.join(r[0] for r in sqlite3.connect('data/panel.db').execute('select agent_token from nodes')))
PY
)" --workers 12 --duration 12

# выдача подписок
python3 tools/loadtest.py --profile sub --sub-token "<token1>,<token2>" --workers 16 --duration 12
```

Полезные флаги: `--json` (машинный результат), `--markdown` (строка для таблицы
ниже), `--token` (Bearer-токен вместо пароля — обязателен, если включена 2FA).

## Результаты в песочнице

Окружение: 2 vCPU (общие, с лимитом), 2 ГБ RAM, панель и нагрузчик на одном
хосте, SQLite в WAL, демо-данные: **3 ноды, 8 клиентов**, Xray не запущен
(ноды отвечают только агентом). Сеть — loopback, поэтому цифры показывают
потолок самого приложения, а не сети.

| Профиль | Воркеры | Длительность | RPS | p50, мс | p95, мс | p99, мс | Ошибки |
| --- | --- | --- | --- | --- | --- | --- | --- |
| agent | 4 | 10 с | 431.9 | 8.9 | 15.9 | 19.1 | 0 |
| agent | 12 | 12 с | 388.3 | 18.0 | 33.1 | 1016.9 | 0 |
| sub | 16 | 13 с | 281.3 | 24.9 | 52.5 | 1057.5 | 0 |
| panel | 16 | 11 с | 258.0 | 33.0 | 93.4 | 1055.2 | 0 |
| panel | 32 | 16 с | 241.9 | 37.1 | 1051.3 | 1268.6 | 0 |

Выводы:

- **Ни одной ошибки и ни одного 5xx** на всех профилях — в том числе на 32
  параллельных воркерах.
- Линейный рост держится до ~4 воркеров на ядро: при 4 воркерах p99 = 19 мс,
  при 32 воркерах на 2 vCPU воркеры начинают бороться за CPU и хвост растёт
  до секунды. Это ограничение песочницы, а не панели: сервер остаётся
  отзывчивым, ошибок нет.
- Профиль `agent` — самый дешёвый (конфиг кэшируется по ревизии), профиль
  `panel` — самый дорогой (дашборд агрегирует 14 дней трафика и здоровье нод).
- 400+ RPS на 2 ядрах означают, что **одна панель спокойно обслуживает десятки
  нод и тысячи клиентов**: агенту хватает 1 запроса в 30 секунд, клиенту —
  одного обновления подписки в 12 часов.

## Проверка на реальных VPS с 2–3 нодами

Песочница не заменяет реальный VPS: там другой диск, другой сетевой стек и
живой Xray. Порядок проверки перед вводом в эксплуатацию:

1. **Панель** — VPS с 1–2 vCPU, установка одной командой:
   ```bash
   curl -fsSL https://raw.githubusercontent.com/Dolov07KBR/DF_Xray/main/install.sh | sudo bash
   ```
2. **Две-три ноды** — на чистых VPS создайте ноды в панели и выполните команды
   «Подключить». Проверьте, что агенты выходят на связь:
   ```bash
   curl -s -H "Authorization: Bearer $TOKEN" https://panel.example.com/api/nodes \
     | python3 -c 'import json,sys; [print(n["name"], n["health"], n["agent_version"]) for n in json.load(sys.stdin)["items"]]'
   ```
   Все ноды должны быть `ok`, версия агента — совпадать с версией панели.
3. **Нагрузка** — запускайте `tools/loadtest.py` с отдельного хоста (не с панели
   и не с нод), иначе меряете сам себя:
   ```bash
   python3 tools/loadtest.py --base https://panel.example.com --profile panel \
       --token "$API_TOKEN" --workers 20 --duration 60
   python3 tools/loadtest.py --base https://panel.example.com --profile agent \
       --node-tokens "$NODE1,$NODE2,$NODE3" --workers 9 --duration 60
   python3 tools/loadtest.py --base https://panel.example.com --profile sub \
       --sub-token "$SUB1,$SUB2,$SUB3" --workers 20 --duration 60
   ```
4. **Что смотреть в Xray** во время нагрузки:
   ```bash
   # на ноде
   journalctl -u xray -f          # нет ли перезапусков и ошибок
   systemctl status dfxray-node   # агент жив, uptime растёт
   ```
   Агент перезапускает Xray только при смене ревизии конфига — под нагрузкой
   перезапусков быть не должно.
5. **Приёмочные ориентиры** для панели на 1–2 vCPU и 2–3 нодах:
   - `agent` и `sub`: 0 ошибок, p95 < 100 мс при 10–20 воркерах;
   - `panel`: 0 ошибок, p95 < 200 мс при 10 воркерах;
   - RSS панели не растёт после прогона (`ps -o rss= -p $(pgrep -f 'app serve')`);
   - в `journalctl -u dfxray` нет `Traceback`.

## Почему панель быстрая

- SQLite в WAL: читатели не блокируют писателей, запись трафика — короткими транзакциями.
- Конфиг Xray собирается на лету по ревизии: `GET /api/agent/config` отдаёт
  `config_revision`, агент не перезапускает Xray, если ревизия не изменилась.
- Задержка до нод кэшируется на 5 минут (`app/latency.py`).
- Ноль внешних зависимостей: нет ORM, нет шаблонизатора, нет async-фреймворка —
  один поток на соединение и stdlib.
